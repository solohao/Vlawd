## 这是什么 / 为什么这么做

在测试过程中，开发者经常会遇到"点击按钮没反应"的问题，通常的做法是：
1. 点击一次 → 没反应
2. 再点几次 → 还是没反应
3. 开始狂点 → 确认真的坏了
4. 手动记录问题 → 容易遗漏

**异常行为检测系统**通过监测"短时间内重复点击"这一模式，自动识别无响应的UI元素，并生成AI可读的问题报告。

### 核心价值

1. **自动识别** - 无需手动记录哪个功能有问题
2. **真实行为驱动** - 基于实际测试行为，不是主观判断
3. **AI辅助修复** - 导出的JSON包含足够的上下文信息，可直接给AI模型
4. **与进度系统解耦** - 异常检测独立于功能完成度追踪

## 工作原理

### 检测逻辑

```
用户点击按钮
    ↓
记录点击时间戳
    ↓
计算时间窗口内的点击次数
    ↓
判断状态：
  - 1秒内 < 5次 → normal（正常）
  - 1秒内 5-9次 → suspicious（可疑）
  - 3秒内 ≥ 10次 → broken（已损坏）
```

### 阈值配置

| 时间窗口 | 阈值 | 状态 | 含义 |
|---------|------|------|------|
| 1秒 | < 5次 | normal | 正常使用 |
| 1秒 | 5-9次 | suspicious | 可能响应延迟或视觉反馈不明显 |
| 3秒 | ≥ 10次 | broken | 确认无响应，已损坏 |

这些阈值在 `feature-anomaly-detector.ts` 中可调整。

## 视觉反馈

### CSS状态标记

```css
/* 正常状态 - 无特殊标记 */
.feature-paint[data-anomaly="normal"] { }

/* 可疑状态 - 橙红色虚线 + 脉冲动画 */
.feature-paint[data-anomaly="suspicious"] {
  outline: 2px dashed rgba(239, 68, 68, 0.5);
  animation: pulse-warning 2s ease-in-out infinite;
}

/* 损坏状态 - 深红色实线 + 淡红背景 + 抖动 */
.feature-paint[data-anomaly="broken"] {
  outline: 3px solid rgba(220, 38, 38, 0.8);
  background: rgba(254, 226, 226, 0.15);
  animation: shake 0.5s ease-in-out;
}
```

### 监控面板

右下角浮动面板实时显示：
- 已损坏功能数量（红色徽章）
- 可疑功能数量（橙色徽章）
- 各功能的点击次数和状态
- 操作按钮：复制报告、下载JSON、重置

## 使用流程

### 1. 开发期测试

正常测试应用，当遇到无响应的功能时：
```
1. 点击按钮 → 没反应
2. 继续点击 → 5次后边框变橙色（可疑）
3. 继续点击 → 10次后边框变红色（损坏）+ 抖动动画
4. 右下角监控面板显示红色徽章
```

### 2. 导出问题报告

测试完成后，有两种导出方式：

**方式A：通过监控面板**
1. 点击右下角监控面板
2. 点击"📋 复制报告"按钮（复制到剪贴板）
3. 或点击"💾 下载JSON"按钮（下载文件）

**方式B：通过DevTools控制台**
```javascript
// 查看报告摘要
__anomaly.list()

// 导出JSON字符串
__anomaly.export()

// 直接下载文件
__anomaly.download()

// 重置所有数据
__anomaly.reset()
```

### 3. AI辅助修复

将导出的JSON粘贴给AI模型：

```
我在测试时发现了以下问题，请帮我分析并修复：

[粘贴 broken-features.json 内容]
```

AI会收到结构化的问题报告，包含：
- 功能ID和严重程度
- 用户行为描述（点击次数、时间窗口）
- 元素信息（选择器、文本、位置）
- 预期行为 vs 实际行为
- 修复建议

## 技术实现

### 核心文件

```
packages/renderer/src/app/
├── feature-anomaly-detector.ts   # 检测器核心逻辑
├── AnomalyMonitor.tsx            # 监控面板UI组件
├── feature-status.tsx            # 集成点（修改）
└── index.css                     # 视觉样式（修改）
```

### 数据持久化

检测数据存储在 `localStorage`，键名为 `aiCursorAnomalyPatterns`，包含：
```typescript
{
  patterns: Map<string, ClickPattern>,  // 各功能的点击模式
  startTime: number                      // 测试开始时间
}
```

### 与FeatureSection集成

```tsx
// feature-status.tsx
export function FeatureSection({ id, children }: Props) {
  const anomaly = useAnomalyStatus(id);

  const handleClickCapture = useCallback((e: React.MouseEvent) => {
    const target = e.target as HTMLElement;
    
    // 异常检测（新增）
    detector.detectClick(id, target);
    
    // 原有进度追踪逻辑
    if (status === "todo") {
      mark(id, "wip");
    }
    recordInteraction(id);
  }, [id, status]);

  return (
    <div onClickCapture={handleClickCapture}>
      <FeaturePaint id={id} anomaly={anomaly}>
        {children}
      </FeaturePaint>
    </div>
  );
}
```

## 与填色系统的关系

| 系统 | 目的 | 触发条件 | 视觉反馈 |
|-----|------|---------|---------|
| **填色系统** | 追踪功能完成度 | 用户交互（自动）+ 手动确认 | 灰度 → 彩色 |
| **异常检测** | 识别无响应功能 | 短时间内重复点击 | 红色边框 + 动画 |

两个系统**独立运行**，互不干扰：
- 一个功能可以是 `wip`（正在开发）+ `broken`（有问题）
- 一个功能可以是 `done`（已完成）+ `suspicious`（响应慢）

## 常见问题

### Q: 为什么有些功能明明有响应，还是被标记为可疑？

A: 可能是以下原因：
1. **响应延迟** - 异步操作耗时较长，视觉反馈不及时
2. **视觉反馈不明显** - 状态变化微小，用户不确定是否生效
3. **阈值过低** - 5次可能对某些场景太敏感，可调整 `SUSPICIOUS_THRESHOLD`

**解决方案：**
- 添加立即的视觉反馈（disabled状态、loading spinner）
- 优化异步操作的响应速度
- 根据元素类型动态调整阈值

### Q: 如何避免误判？

A: 代码中已实现部分容错：
```typescript
// 可按元素类型调整阈值
const getThreshold = (element: HTMLElement) => {
  if (element.tagName === 'INPUT') return 3;  // 输入框更敏感
  return 10; // 按钮默认10次
};

// 可通过Shift键标记为压力测试
if (e.shiftKey) {
  // 不计入异常检测
}
```

未来可扩展：
- 识别特定UI模式（如音量滑块）自动豁免
- 学习用户正常点击频率，动态调整阈值
- 结合实际DOM变化判断是否真的无响应

### Q: 导出的JSON太大怎么办？

A: 当前限制：
- 每个功能最多保留20次点击时间戳
- 元素文本内容截断到100字符
- 只导出 `suspicious` 和 `broken` 状态的功能

如果仍然过大，可以：
- 在监控面板中选择性重置某些功能
- 只导出 `broken` 状态（修改 `exportReport` 过滤条件）

## 后续优化

1. **智能阈值** - 根据元素类型、历史数据自动调整
2. **DOM变化检测** - 结合 MutationObserver 判断是否真的无响应
3. **性能影响识别** - 检测点击后CPU/内存飙升
4. **批量修复建议** - 对同一类问题提供统一修复方案
5. **自动截图** - 检测到异常时自动截图保存上下文
6. **团队协作** - 支持导出/导入，团队成员共享测试结果

## 使用建议

**DO：**
✅ 在开发期日常测试中保持监控面板开启  
✅ 遇到无响应功能时自然地多点几次（不用刻意）  
✅ 定期导出报告，批量给AI修复  
✅ 修复后重置数据，重新测试验证  

**DON'T：**
❌ 不要为了"凑数"而故意狂点正常功能  
❌ 不要只依赖阈值判断，手动验证是否真的有问题  
❌ 不要在生产环境开启（构建时自动禁用）  
❌ 不要忽略 `suspicious` 状态，它们通常代表UX问题
